# 精简审查

目标：找出有实际影响的缺陷和可安全删除的负担。不做风格评比，不为审查增加新机制。

## 范围

- 按用户指定范围审查：PR、分支、提交、diff、文件或模块。比较分支时以合并基点为准。
  未指定时优先审当前未提交改动（含暂存、未暂存和相关新增文件）；仍无可确定范围再询问。
- 只补足判断所需的上下文，不默认全仓扫描。结论必须由当前代码与验证结果支撑。
- 审改动时优先报本次引入或加重的问题；既有问题仅在用户要求审现有实现、或它直接影响
  本次改动时提出，并写明归属。
- 默认只报告、不改文件。用户要求修复时逐项做最小修改并验证，不顺带重构。

## 检查重点

- **死代码**：无消费者的参数、导出、状态和不可达分支。建议删除前核对动态注册、配置、
  外部调用和公共合约——局部搜索无命中不能证明可删。
- **冗余负载**：重复 I/O 或计算、无消费者的数据、可推导却重复保存或同步的状态。
  指出具体路径与额外成本。
- **脆弱实现**：依赖隐含顺序、跨异步等待使用过期状态、失败后留下不一致数据，或用兜底
  吞错掩盖根因。给出触发条件、预期行为与实际后果。
- **无依据机制**：抽象、配置、兼容、重试、兜底。问"删掉它，哪个现有需求、调用方或可信
  失败场景会受影响？"用实际行为与合约判断价值。

## 判断边界

- 优先修根因与操作顺序，复用已有路径；不为一个问题建议通用框架。
- 不因文件长、局部相似、个人风格或假想未来报问题，不强凑数量。
- 判断一段逻辑是否多余时，先看它是否保护输入边界、安全、公共合约或数据一致性。
- 证据不足的高影响疑点单列"待核实"，说明缺什么证据，不当作确定缺陷。
- 报告里区分**已执行**的验证与**建议执行**的验证；不改的文件不声称已修。

## 输出

先报发现，按实际影响排序。每条包含：

- **位置**：文件路径与行号。
- **证据与影响**：当前调用链、需求或可复现触发条件，以及具体后果或负担。
- **最小建议**：删什么或改哪个根因；确需新增机制时说明现有路径为何不足。
- **验证**：能验证该结论的最小测试或检查。

同一根因合并报告。没有可靠发现时明确写"未发现有充分证据的问题"，并列出审查范围与
未验证项，不声称代码已无缺陷。
